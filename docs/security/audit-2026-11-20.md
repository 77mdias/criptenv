# Auditoria de Segurança — CriptEnv

- **Data:** 2026-11-20
- **Escopo:** revisão estática do código-fonte (`apps/api`, `apps/cli`, `apps/web`) da aplicação própria.
- **Método:** leitura de código focada em segurança (authz, cripto, manejo de tokens, SSRF, injeção, XSS), sem teste dinâmico contra a URL ao vivo.
- **Veredito geral:** **nenhuma vulnerabilidade HIGH ou MEDIUM de alta confiança.** 1 item de baixo risco (defesa em profundidade) encontrado e **corrigido** (ver INFO-1).

---

## 1. Resumo executivo

O código é defensivo de forma consistente, com os padrões corretos justamente onde costumam surgir bugs: SSRF com IP pinado, fail-closed em assinaturas, hashing de tokens de alta entropia, env-scoping cross-project, e 2FA com lockout. As classes clássicas de injeção/RCE estão ausentes (sem `eval`/`exec`/`pickle`/`yaml.load`/`subprocess` com shell/SQL por f-string).

Um único item acionável (INFO-1) foi corrigido nesta mesma sessão e entregue no PR #104.

## 2. Áreas revisadas — o que está sólido

| Área | Achado |
|------|--------|
| Injeção SQL | Apenas SQLAlchemy ORM parametrizado. Zero f-string/`%`/concat em `execute()`. |
| RCE / deserialização | Sem `eval`/`exec`/`pickle`/`yaml.load`/`os.system`/`shell=True`. |
| Hash de tokens | Sessão/API key/CI/reset/verificação → SHA-256 de token aleatório de alta entropia (`token_urlsafe` 48–64B). Senha → bcrypt. |
| Cripto de integração | AES-256-GCM + HKDF-SHA256, nonce 12B via `os.urandom`, segredo ≥32 chars validado. URL de webhook cifrada em repouso. |
| Webhook Mercado Pago | HMAC-SHA256, `compare_digest`, **fail-closed** se o segredo não estiver configurado. |
| Login CLI | PKCE S256 com `compare_digest`, callback **só loopback**, device flow single-use (`consume`). |
| 2FA | Lockout por desafio (5 tentativas), contagem **antes** da checagem, fail-closed se o storage cair; backup codes gastos no uso. |
| CORS | Validador rejeita `*` quando `allow_credentials=True`. |
| `DEBUG` | Forçado `false` em produção (o flag `Secure` do cookie depende disso). |
| XSS frontend | 3 `dangerouslySetInnerHTML`: 2 scripts de tema estáticos + 1 JSON-LD de strings i18n (`t()`). Sem entrada de usuário. |
| Authz de API key | `require_api_key_project` responde **404** fora do projeto (não vaza existência); escopo de ambiente idem. |
| Billing / Mercado Pago | `process_webhook_notification` é o **único** caminho para `PAID` e sempre re-consulta o MP (status autoritativo). IDs são UUID. Sem IDOR nem forja de pagamento. |
| Chat de suporte | Chave Anthropic 100% server-side; única ferramenta é `search_docs` read-only; `role` travado em `user`/`assistant`; nada da conversa é logado. |
| Rotação de secrets | `_check_access` valida membership **e** que o environment pertence ao projeto; escrita gated em `admin`. |
| CLI (Python) | Arquivos `0o600`, dir `0o700`; secrets só em memória no `run` (nada em disco); `subprocess` sempre com lista de args; sessão cifrada AES-GCM. |

## 3. INFO-1 — redirect_uri do OAuth a partir de `X-Forwarded-Host` (corrigido)

- **Severidade:** baixa (defesa em profundidade).
- **Local:** `apps/api/app/routers/oauth.py` — `_get_public_request_base_url`.
- **Descrição:** o `redirect_uri` do OAuth era montado a partir de qualquer `X-Forwarded-Host`, sem validação.
- **Impacto real:** limitado — o roubo do `code` já era barrado pela allowlist de `redirect_uri` do provedor, e os redirects finais já usavam `FRONTEND_URL`. O risco residual era um `X-Forwarded-Host` forjado direcionar o `redirect_uri`, caso a borda (Cloudflare Tunnel) não sobrescrevesse o header.
- **Correção:** o header passa a ser honrado **somente** quando o host bate com um host que a API serve de fato (`API_URL` ou `FRONTEND_URL`); qualquer outro valor cai no `API_URL` canônico registrado no provedor. Modelo de deploy preservado: a API roda interna (`API_URL=localhost:8000`) e o host público legítimo chega via `X-Forwarded-Host` (= `FRONTEND_URL`: ngrok em dev, domínio de prod em produção).
- **Testes:** novo caso de spoof (host desconhecido → ignorado) + ajuste do teste de forwarded-host.
- **Entrega:** PR #104 (`fix/oauth-forwarded-host-allowlist`), CI 100% verde.

## 4. Notas informativas (abaixo do limiar de report)

- **INFO-2 — API keys são read-only por design** (`VALID_API_KEY_SCOPES` só `read:secrets`/`read:audit`). Rotas de escrita barram o prefixo `cek_` com 403 em `get_current_user`. Mantido.
- **INFO-3 — chave de sessão do CLI em claro ao lado do DB** (`session.py`): a cifra protege contra leitura casual; a proteção real é a permissão `0o600`. Mesmo modelo de gh/aws/doppler. Aceitável.
